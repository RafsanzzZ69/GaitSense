to a **working, tested backend workflow connected to MongoDB Atlas**.

## How much is complete?

These are **rough scope estimates, not measured completion percentages or promises**.
The denominator is the first working mobile/web research MVP, not a clinical product.

| Area | Approximate readiness | Main work remaining |
|---|---:|---|
| Core database | 90% | Final frontend-driven field adjustments, deployed backup/retention drills and access roles |
| Core backend | 75–80% | Frontend contract integration, email recovery/verification, deployment hardening, broader video/worker tests |
| Mobile/web product | Still a prototype | Replace mock data, authentication screens, real camera/upload, report/replay/history UI |
| Research/clinical validation | Early proof of concept | More independently labelled participants, protocol/event validation, subject-wise evaluation, external testing |

Most **core backend/database plumbing** is now implemented. The overall one-year
project is still much earlier—roughly **20–25%** by feature scope—because usable
mobile workflows and trustworthy gait/health interpretation remain substantial work.
A defensible research result takes more work than creating API endpoints.

## Next build order

1. **Connect the existing Expo frontend to this backend:** registration/login, consent,
   profile, video upload, job status, real measured report and history. Do not start a
   second unrelated frontend or database.
2. **Complete the recording experience:** actual mobile recording, permissions,
   framing/timing guidance, upload progress, retry UX and skeleton replay.
3. **Improve and validate measurements:** manually inspect step events, handle variable
   frame rates and turns, formalize calibration, quality gates, units and comparability.
4. **Expand the dataset and train reproducibly:** independent reference walking-speed
   labels, subject-level splits, baseline comparisons, confidence intervals and external
   validation. The existing four-person PoC does not establish reliability.
5. **Deploy and harden:** hosted API/worker, private object storage, HTTPS, backup/restore,
   email services, monitoring, realistic load/concurrency/device tests and consent review.

## Deliberately not claimed as complete

No validated health score, disease detection, fall-risk model, joint-stress diagnosis,
exercise prescription or clinical approval. No production-ready "works everywhere"
guarantee. The backend reports explicitly mark unsupported measurements as unavailable.
The existing Expo screens still use mock data until the next integration milestone.

## Saved connection status

Compass has a saved Atlas connection. Backend credentials are persistent in the ignored
`backend/.env`; they are not required to be pasted again on every backend start.
VS Code's MongoDB extension also contains globally saved Atlas entries using encrypted
`vscode.SecretStorage`, but its original SRV connection failed DNS lookup. A tested
replica-set seed connection was sent to VS Code under **GaitSense Atlas (saved)**. Its
one-time Open/Connect confirmation must be approved before success can be verified.
The **GaitSense Atlas: Save connection in VS Code** task can reopen that flow without
exposing the password in workspace settings. A saved connection is not an always-on
network connection; password/IP/cluster changes can still require reconnection.
